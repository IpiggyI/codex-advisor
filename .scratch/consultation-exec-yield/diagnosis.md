# 后台执行咨询的边界检查失败诊断

日期：2026-11-19。范围：只诊断，不修改插件、安装、失败计数或用户进程。

## 当前状态与待评审结论

状态：用户于 2026-11-20 决定删除该检查，已在 `0.3.11` 本地实现，见 `.scratch/consultation-robustness/plan.md`。尚未提交、推送或安装。

- 报错 `History changed beyond the unfinished consultation boundary.`（`pairing`）的原因已确认。调用方在 code mode 的 `exec` 中自行设置了很短的 `yield_time_ms`。宿主先把后台执行单元的输出写入会话记录，咨询服务器随后才读取。
- `consult_context.py:348-349` 要求咨询调用之后没有任何 `response_item`，因此拒绝。重建在咨询调用处停止，之后的记录不进入历史。这条检查对重建结果没有影响。
- 问题从 2026-10-28（`0.164.0`）就已存在，不是 `fa63c8c` 引入的。触发条件是模型选择的 yield 时长，不是宿主更新。
- Windows 线程 `01a1f678-71ae-7ce1-aade-ec2b7a3575b1` 因三次同类失败，失败计数已达 3，咨询已在该线程停用。

## 已验证原因

宿主 MCP 元数据中的 `itemId` 指向外层 `exec` 的 `custom_tool_call`。`_reconstruct()` 找到这条边界后，检查其后是否还有 `response_item`，如有就返回 `pairing`。

Windows 会话 `C:/Users/Shy/.codex/sessions/2026/11/20/rollout-2026-11-20T09-00-50-01a1f678-71ae-7ce1-aade-ec2b7a3575b1.jsonl`，宿主版本 `0.169.0-alpha.11.1`，以下记录号从 0 计：

| 记录 | 时间（UTC） | 内容 |
|---|---|---|
| 26 | 01:01:05.141 | `exec`，输入 `// @exec: {"yield_time_ms": 50}` 加 `process_consultation({})` |
| 28 | 01:01:05.213 | 同一 `call_id` 的输出 `Script running with cell ID 2` |
| 31 至 44 | 01:01:09 至 01:01:28 | 调用方在咨询运行期间继续调用其他工具 |
| 48 | 01:01:30.534 | `wait` 读到失败结果，`recordIndex` 为 26，`failureCount` 为 1 |

第 52 条（yield 50 毫秒）和第 337 条（yield 100 毫秒）重复同一过程，失败计数到 3，`consultationDisabled` 为 true。同一线程第 78 条调用没有设置 yield，后台输出约 31 秒后才写入，咨询成功。

## 复现

`reproduce.py` 把真实会话记录截到指定记录号，放进临时宿主目录，再调用当前 `reconstruct()`：

```
python3 .scratch/consultation-exec-yield/reproduce.py <rollout> 26 27   # OK items=13
python3 .scratch/consultation-exec-yield/reproduce.py <rollout> 26 28   # FAIL pairing ... recordIndex 26
```

第 337 条读到 338 时通过，读到 340 时失败。结果确定，每次不到一秒。

## 历史同类失败

两台机器上全部 6 次该报错都是同一原因。每一例在读到边界后那条后台输出时失败，去掉这一条就通过。

| 会话记录 | 边界记录 | yield | 宿主版本 |
|---|---|---|---|
| Windows `2026/11/20/rollout-2026-11-20T09-00-50-01a1f678-…` | 26、52、337 | 50、50、100 毫秒 | `0.169.0-alpha.11.1` |
| WSL `2026/11/18/rollout-2026-11-18T05-55-36-01a1eef0-…` | 21 | 5 毫秒 | `0.170.0` |
| WSL `2026/11/18/rollout-2026-11-18T05-10-43-01a1eec7-…` | 331 | 1 毫秒 | `0.170.0` |
| WSL `2026/10/28/rollout-2026-10-28T13-18-04-01a180f1-…` | 31 | 1 毫秒 | `0.164.0` |

yield 不超过 100 毫秒、结果可知的调用共 7 次，失败 6 次。成功的一次是 WSL `rollout-2026-10-28T14-07-56-01a1811f-…` 第 254 条：调用记录与后台输出相隔约 256 毫秒，服务器先读完了文件。这是一个高命中率的竞争，不是每次必现。使用默认 yield 的 475 次调用中只有 1 次 `pairing`，属于下文已修复的带名称输出。

## 删除检查后的重建结果

在临时副本中删除第 348-349 行，读取上述 5 个案例的完整最终文件。重建结果与当前代码在边界时刻读取的结果完全相同（逐项比较 `reconstruct()` 返回值）。

删除检查会失去两项检测：调用方已经继续工作，以及宿主已经为这次调用写入结果。直接 `function_call` 时调用方阻塞等待，所以这条检查实际上只在后台 `exec` 中触发。

## 结构性原因

- 咨询依赖四个宿主私有接口：MCP `_meta`、会话记录格式及其写入时机、App Server `thread/inject_items` 协议、推理请求追踪与模型目录。约 8 周内观察到 14 个宿主版本（`0.157.0` 至 `0.170.0`，另有 Windows 桌面 alpha 版本）。
- 每项检查都失败即拒，并计入三次停用。有的检查守护的是“调用方同步等待”这类假设，不保护咨询内容。
- `tests/consultation_corpus_replay.py:77-94` 在边界处截断文件，相当于服务器在调用瞬间读取，看不到时序和调用方式问题。ADR-0006 记载 parallel tool races 未经认证。`release-0.3.10/acceptance.md` 记载，在 WSL 的 CLI `0.169.1` 上，宿主模式差异检查覆盖 18 类，语料回放 31913 个位置，没有普通失败。这项检查通过时，本问题已经存在，说明截断回放看不到它。没有记录显示这项检查在 Windows 桌面 alpha 版本上运行过。
- 一部分“新报错”是旧缺陷首次被触发，例如本问题。

## 修复方向（待选）

1. 推荐：删除 `consult_context.py:348-349`。同时增加真实案例的精简回归用例，以及不在边界截断的语料回放变体，并更新 ADR-0006 的边界校验条文。
2. 备选：收窄为只在直接调用自己的 `call_id` 已有结果时失败，其余同上。
3. 只作补充：在调用规则中要求不缩短 yield。模型在 3 个宿主版本、两台机器上都自行选了 1 至 100 毫秒，文字规则不能保证遵守。

任一修复都需要：修改发布文字时同步 `docs/zh/` 镜像，编写版本手册，推送，并在两台机器上重装。推送、重装以及是否重置上述线程的失败计数，都需要用户另行授权。
