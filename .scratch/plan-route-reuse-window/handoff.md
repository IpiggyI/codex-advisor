# 来自 fable-advisor 6.2.0 的交接：全局规划、路由校验、续用窗口

日期：2026-10-04。核对基线：本仓提交 `bffc0ce`，插件 `0.3.2`。

fable-advisor 在 6.1.0 的试用中暴露了三个问题，6.2.0 已修复并发布（fable-advisor 提交 `fd1904c`）。本文件对照本仓的条文和机制，判断这三个问题是否也存在。本文件只做对照与交接，没有改本仓的其他文件。它只对照条文和机制，没有查本仓的使用记录。

fable-advisor 仓里的来源：

- 决策记录：`docs/adr/0030-global-plan-route-gate-reuse-window.md`；
- 问题报告：`.scratch/trial-6-1-0-feedback/problem-report.md`，第 3 至 5 节是三个问题的经过与成因；
- 任务件：`.scratch/trial-6-1-0-feedback/spec.md`，D1 至 D3 是三项决策的细则。

## 一、三个问题在 fable-advisor 里的表现

1. **逐票验证。** 主会话把前端拆成 5 张票，逐张派发、逐张验收、逐张提交。改同一张表的票没有并成一份契约。一张票的渲染验收约 8 分钟，原计划每张票各做一轮。主因是已有规则没有执行；条文也缺两样：派发前写下整个任务的验证规划，以及提交边界与验收边界分开。
2. **档位形同虚设。** 4 张票首轮直接进 `rescue`，都没有椰椰的声明。准入规则只写在条文里，派发说明不写档位，没有程序核对。新票经续发进入已有会话，绕过了首次派发时的把关。
3. **冷会话续用。** codex 车道在上回合结束 143.7 分钟后续用会话，第一次请求的 146,061 个输入词元只命中缓存 3,968 个。返工和续用的条文都没有时间条件，新票能否续用也没有规定。

## 二、本仓的对照

### 问题一：部分存在

本仓已覆盖的部分：

- `plugins/codex-advisor/skills/orchestration/SKILL.md:81-91`：派发前检查依赖、所有权与可用槽位；票的边界、派发数量与验证批次分开决定；共用昂贵准备的检查合并；有依赖的票按实际状态更新后再派。
- `SKILL.md:95-99`：主代理亲自检查全部实际改动，包括 worker 写的验收测试，并确认测试能因目标需求而失败。这比 fable-advisor 6.1.0 的验收要求更严。
- `SKILL.md:101-110`：每个验证批次只有一个执行者，只跑一次。

本仓的缺口：

- 条文要求派发前「检查」与「决定」，不要求把规划写进任务件。fable-advisor 的成因之一是规划单位落成了票据表，检查按票写。
- 编排技能全文没有提交规则（`grep -i commit` 在 `skills/orchestration/` 下无结果）。fable-advisor 的成因之一是把提交边界和验收边界绑在一起。
- 并发 worker 共用一个工作目录时没有隔离规则。`SKILL.md:81` 的所有权与第 88 行「不要把共享文件拆给名义上独立的所有者」只防同一文件的冲突。

### 问题二：存在

- **准入只是文本规则。** `SKILL.md:59-62` 与 fable-advisor 6.1.0 的「Stage 1」相同：新工作从 `mainstay` 开始，识别出关键难点时可以从 `crux` 开始，`rescue` 首轮只凭椰椰的声明。派发说明不写档位依据。
- **钩子只核对型号与强度。** `plugins/codex-advisor/hooks/hooks.json:12-13` 是 `PostToolUse`，匹配器只有 `collaborationspawn_agent`。`plugins/codex-advisor/scripts/advisor-hooks.py:133-155` 只比较子线程实际的型号与强度和入口模板，确认行注明不检查工作目录与权限。它不检查档位依据。`PostToolUse` 在派发之后运行，按事件语义不能拒绝派发；这一点没有在 Codex 上探测过，见第四节第 3 项。
- **续发不经过钩子。** 匹配器只列派发工具。经续发进入已有线程的新工作不受钩子检查。续发的工具名和它能否被钩子匹配，本文件没有核实。
- **档位句与档案表冲突。** `SKILL.md:68` 写「A capability tier is set by its models; effort is a finer grade inside the tier.」。`plugins/codex-advisor/skills/orchestration/references/routing-profile.md:15` 的 Worker 行里，`gpt-6.1-sol` 同时出现在 `mainstay`（`gpt-6.1-sol[medium*, high]`）、`crux`（`gpt-6.1-sol[xhigh]`）与 `rescue`（`gpt-6.1-sol[max]`），`gpt-6-astra` 同时出现在 `crux` 与 `rescue`。fable-advisor 6.1.0 有同样的冲突，见问题报告 4.2 第 5 条。
- **型号声明怎么定档没有写。** 例如椰椰声明 worker 用 `gpt-6-astra`，而 Worker 行的 `gpt-6-astra` 只在 `crux` 与 `rescue`。条文没有说这时取哪一档。fable-advisor 的问题报告推断，主会话把家族声明读成了可以任选强度（4.2 第 2 条，标为推断）。

### 问题三：存在

- `references/recovery.md:24-25`：R1 是同一线程、同一拨盘的返工票。
- `recovery.md:44-52`：同型号、同强度的 worker 返工可以经续发（条文原文 `native follow-up`）续用线程。这里没有时间条件。第 51 至 52 行写明这是生命周期政策，不是缓存行为的结论。
- 条文没有规定新票能否续用已有线程，也没有规定线程上次活动时刻的来源。
- 已覆盖的部分：`recovery.md:47-50` 要求改强度、改型号或改角色时新开线程。fable-advisor 的一张新票在续用时改了强度，缓存几乎全部失效；只有这一个样本，不能证明改强度是原因（问题报告 5.1）。
- fable-advisor 的缓存证据来自 Codex CLI 会话。本仓的原生子线程走同一家服务，但它们的缓存寿命没有在本仓测过。

## 三、fable-advisor 6.2.0 的做法

下面是 fable-advisor 的决定，供参考。它们不是本仓的决定。

1. **全局规划（ADR 0030 决策 1 至 3）。**
   - 任务有两张以上的票时，主代理在第一次派发前把四项写进任务件：依赖、契约（共用文件或同一区域的票并成一份）、隔离（并发契约各用独立的工作目录）、宽检查（覆盖哪些契约、由谁跑、何时跑）。
   - 没有全局的阶段屏障；一份契约只等它真正需要的结果。
   - 提交按授权和回滚边界拆，与验收分开。问提交粒度时，给出按契约提交的选项。
   - 验收对照契约逐条核对报告、检查证据和承载行为的文件的限定路径差异。
2. **路由与机械校验（决策 4 至 6）。**
   - 每次派发写明角色、档位、拨盘；高于 `mainstay` 时加依据种类与 `ref`。续发给已有会话的消息也写路由。
   - 依据种类按角色和档位定，例如 worker 的 `crux` 收 `key-difficulty`、`failure`、`user-declaration`。
   - 档位取满足三个条件的最低一档：不低于难点或升级梯定下的档位；格里有符合声明的候选；有该档接受的依据。型号或家族声明可以作 `crux` 的依据，不作 `rescue` 的准入。
   - 程序只查依据存在、格式合规，不查真假。runner 在启动 CLI 前校验；Claude Code 上用 `PreToolUse` 钩子拒绝不合规的派发和续发。
   - 档位句改为：档位是每个角色的一组拨盘，同一型号可以按强度分在不同档位。
3. **续用窗口（决策 7）。**
   - 返工、修正契约、被时钟切断后的续跑、续发、新票，都只在窗口之内续用。
   - 窗口取值是椰椰声明的续用政策，不是实测的缓存寿命。codex 车道是 30 分钟。
   - 窗口从车道上次活动算起；时间不明时按超窗处理。超窗时在同一档位、同一拨盘上新开会话，带上缺陷、原契约、上轮报告和回执。
   - 新票只在四个条件同时成立时续用：同一区域、确实需要共享上下文、同一拨盘、在窗口之内。

## 四、要椰椰决定或要先核实的事

1. 本仓是否做这三项，范围和版本号是多少。
2. 原生线程的续用窗口取多少。fable-advisor 的 codex 车道是 30 分钟。
3. 机械校验的形状。先核实宿主事实：
   - Codex 的钩子能否在派发之前拒绝；
   - 续发用哪个工具，钩子能否匹配它；
   - 拒绝在各审批模式下是否生效。
   fable-advisor 用无界面会话做的阶段零探针是先例，见其任务件 D2「宿主事实」。
4. 档位句与表的冲突怎么解：照 fable-advisor 改档位句，或改表让同一型号只在一档。
5. 本仓的 `Architect mode`、过程咨询与 fable-advisor 不同。移植时以本仓 ADR 0003 至 0009 为准。
