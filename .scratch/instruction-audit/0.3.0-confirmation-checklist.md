## 如何记录裁定

用户审阅某一项之前，保持该项未勾选。审阅后勾选，并把"裁定"字段改为 `keep`、`simplify`、`remove`、`update`、`defer` 或 `reject` 之一，再写明商定的范围。包含多个步骤的项，每个步骤各有一个复选框，可以单独批准。勾选只表示裁定已记录，不表示已实施或已验证。

凡是涉及安全、权限、隔离或验证的项，也列在[保障变更登记](#保障变更登记)中，需要在那里单独作出明确裁定。

### 机器解析的文本（任何修改都必须遵守的硬约束）

`routing-profile.md` 是一个接口，有四个脚本读取它：

- `scripts/consult_context.py` 的 `route()` 在全文中收集所有 `` `ca_name` gpt-…[efforts] `` 形式的匹配，存入一个字典。
  - 正文里后出现的重复写法会悄悄覆盖表格中的值。
  - 它把调用方所在档位 `Advisor` 单元格里第一个列出的推理等级当作咨询用的推理等级。
  - 它依赖 `compare model first: A < B < C. Compare effort second: x < y < z.` 这一句的原样结构。改写这句话后，所有咨询都会失败，并报 "Routing profile ordering is unavailable."。
- `scripts/advisor-hooks.py` 要求所有 `` `ca_advisor_…` model[ `` 匹配中只出现一个模型。
- `scripts/verify.sh` 的 `parse_profile()` 有两条要求：
  - 在所有表格行中，每个 `ca_` 名称只出现一次；
  - 当且仅当单元格里只有一个不带星号的推理等级时，模板才有固定字段。
- `scripts/verify-hooks.py` 在一个反例测试夹具中精确替换子串 `` `ca_advisor_rescue` gpt-6-astra ``。

`consult-posture.md` 中的姿态块会被逐字节复制到各入口，也会由 `SessionStart` 钩子注入。`verify.sh` 会检查英文副本和中文副本。

### 发布连带影响

对模板或 `plugins/codex-advisor/` 下任何文件的修改都会随插件发布。发布需要依次完成：

1. 提升 `plugin.json` 的版本号。
2. 新增 `docs/releases/<version>.html`（见[版本说明书规则](../../docs/agents/version-manual.md)）。
3. 在同一次提交里更新中文镜像。
4. 推送。
5. 在 WSL 和 Windows 两端执行升级和重装步骤。

模板一改，已安装入口就会和模板逐字节不一致，直到重新运行安装器。在此之前，派发前的 `--check-role` 检查会失败，受影响的派发都会停在待定状态。

### R17：钩子被跳过和派发检查通过，表现完全相同

- [ ] 审阅 R17 并记录裁定。

**裁定：** 待裁定。需要明确批准，因为它会改变一项验证保证。

**分类：** 纠正一项验证声明。代码方案属于功能变更。

**位置与原始指令：**

- [operations.md 第 345–348 行](../../plugins/codex-advisor/skills/orchestration/references/operations.md)："Matching dispatches are silent. … No manual inspector run is needed for this comparison."
- [README 第 127–129 行](../../README.md)有相同内容。
- operations.md 第 331–333 行："the host skips untrusted hooks and prints a startup warning pointing to `/hooks`. The plugin does not modify trust state or add its own untrusted-hook detector."
- operations.md 第 95–97 行和第 110–111 行仍要求调用方 "Validate role, model, effort, thread, parent association, working directory, and observed permissions."

**已核实的情况：**

- 派发检查通过时没有输出；钩子未被信任而被跳过时，同样没有输出。调用方无法区分这两种情况。
- 启动警告是否会进入模型上下文，没有验证。
- 钩子只检查模型和推理等级。文档没有说明检查器的其他检查项（父线程、工作目录、权限）是否仍需手动执行，也没有说明何时执行。
- 另一个钩子有同样的问题：`SessionStart` 被跳过时，不会注入姿态，主代理也收不到任何姿态缺失的信号。技能正文要求阅读 `consult-posture.md`（SKILL.md 第 131–134 行），可以部分弥补这条路径。

**建议：** 二选一。

- (a) 只改文档：
  - 做法：把"无需手动运行检查器"改为以钩子确实在运行为前提；写明哪些检查仍需手动执行，以及触发条件，例如只在验收依赖隔离或工作属于高风险时执行。
  - 局限：`SessionStart` 在运行，不能证明 `PostToolUse` 已被信任，因为信任是按每个钩子的哈希分别授予的。
- (b) 改代码：检查通过时钩子输出一行简短确认，这样没有输出就意味着钩子没有运行。每次派发会增加少量上下文。

无论选哪种，都要写明：当主代理的上下文中没有 `SessionStart` 注入的姿态时，应该怎么做。

**影响与失去的覆盖：** 按现有文字，主代理可能把一次未经检查的派发当作已核实。方案 (b) 能恢复这项保证；方案 (a) 能缩小缺口，但不能消除缺口。

**验证（未运行）：** 在临时 `CODEX_HOME` 中保持 `PostToolUse` 未被信任，然后用错误的推理等级派发一个由调用方选择推理等级的入口。通过标准：主代理没有把这次派发报告为已核实。
