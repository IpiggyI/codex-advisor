第一章

安装与更新

需要支持插件、原生自定义代理、MCP 和钩子的 Codex，以及 Python 3.11 或更新版本、POSIX 命令行和 jq。本版咨询协议与钩子元数据已在 Codex 0.157.0 验证；宿主协议、会话记录或缓存布局变化后，需要重新核验。

codex plugin marketplace add https://github.com/IpiggyI/codex-advisor.git
codex plugin add codex-advisor@codex-advisor
plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
test -n "$plugin_dir" && test "$plugin_dir" != null && test -d "$plugin_dir" && test -f "$plugin_dir/scripts/install-agents.sh" && sh "$plugin_dir/scripts/install-agents.sh"
sh "$plugin_dir/scripts/install-agents.sh" --check

配套安装器将十三个入口写入 $CODEX_HOME/agents，未设置时使用 ~/.codex/agents。它覆盖本插件有变化的模板，并删除 0.1.0 与 0.2.0 共十九个退役文件名；不修改其他代理或主会话配置。符号链接、非普通文件、不合法祖先和危险目标路径会在写入前被拒绝。

安装后打开全新交互会话，在 /hooks 中审阅并信任两条插件钩子。安装或启用插件不会授予信任。尚未信任时，宿主跳过钩子并显示启动警告。分别确认编排技能、十三个入口和 codex_advisor MCP 服务器的 process_consultation 工具已发现。

更新每一侧安装

已安装市场从 GitHub 仓库获取版本；未推送的提交不会进入安装副本。WSL 和 Windows 使用各自的原生 Codex 与配置目录。Windows 中的这些命令需要 Git Bash 及相应依赖。

codex plugin marketplace upgrade codex-advisor
codex plugin remove codex-advisor@codex-advisor
codex plugin add codex-advisor@codex-advisor
plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
sh "$plugin_dir/scripts/install-agents.sh"
sh "$plugin_dir/scripts/install-agents.sh" --check

随后开启新交互会话。更新改变钩子定义时，再通过 /hooks 审阅；信任绑定当前钩子的哈希值。--check 只检查，不写文件；模板缺失、内容漂移或退役文件残留都会失败并列出具体项。

不要手改已安装入口。开发时只在临时 CODEX_HOME 中添加本地仓库路径；不要把真实安装改指向未发布工作树。

第二章

使用方式

使用 $codex-advisor:orchestration 实现并验证这项功能。

任意主会话都可以自己实现、委派，或两者并用。主会话负责目标、拆解、调度和验收，在用户的范围、保留决策与资源限制内选择执行方式。普通分配不需要逐次请求许可。

探索者只读收集证据、来源位置和缺口。执行者接收目标、文件归属、接口、约束和核验要求，负责局部实现与排错，保留其他人的改动，不再委派实现。顾问负责过程建议或独立验收；两者入口和上下文要求不同。

只做设计与调度的模式

本任务使用 $codex-advisor:orchestration 的 Architect 模式。

Architect 模式需要明确授权，覆盖当前任务及其后续。主会话保留设计、合同、调度和验收；范围内每一处实现编辑和修正都必须委派。工单、规格、模型身份或未接受方案本身不会打开该模式。无关任务需要新授权，除非用户明确授权整段会话。

第四章

准入与升级

通常从主力开始。已识别关键难点，或多个约束需要联合处理时，可以首轮进入攻坚。更窄的攻坚准入规则仅保留记录，不启用。后援只能在攻坚发生能力失败后，或由用户明确声明启用。

完整尝试包含实现、排错和核验，最终验收失败或确实无法完成。原尝试与同一线程、同一设置的返工都失败，且原因归于能力，合计才算一次能力失败。环境问题、缺失事实、合同缺口和中途测试失败不推动升级。

  1. R1

    先在原线程发返工票，说明被违反的要求、复现、预期行为和核验方法。执行者负责修正。

  2. R2

    返工后形成能力失败，按主力、攻坚、后援、用户的顺序移交。除非没有其他选择，不在失败档位内换模型，也不降低模型等级。同模型接手必须提高强度。

  3. R3

    同一模型最多提高一次强度。模型、强度或角色改变都需要匹配入口的新线程；同设置返工可以复用原线程。

  4. R4

    工具反复失效、失控或触碰保留项等重大执行问题，可以跳过返工，记为一次能力失败。

从攻坚起步的任务在一次攻坚能力失败后进入后援。移交前停止冲突写者，检查实际状态，保留有用改动，并交接已完成项、失败证据和剩余工作。

第五章

过程咨询与独立验收

过程咨询

自动携带上下文

主会话、执行者和探索者以空对象调用 process_consultation。顾问自动取得当前有效上下文，没有工具，返回计划、修正或停止建议。调用者不用编写摘要或数据包。

独立验收

新线程检查交付物

高风险工作或用户明确要求独立审查时，主会话检查后，另开顾问线程发送验收数据包。顾问检查真实改动与证据；过程咨询、执行者自评和检查执行不能代替它。

主力入口咨询 gpt-6-astra[low]，攻坚咨询 gpt-6-astra[high]，后援咨询 gpt-6-astra[xhigh]。主会话选择不弱于自身设置的最低顾问设置；没有合格设置或模型标识未知时，选择最强设置。咨询顾问没有自己的升级路径。

按精确模型标识选择咨询姿态

  • 调用者与顾问模型不同，使用完整姿态：实质工作前、遇到阻滞时、改变方法前、宣布完成前咨询。定向找文件和读来源不算实质工作。短任务的下一步直接由刚读到的工具输出决定时，可以免于咨询。
  • 模型相同，使用精简姿态：只在多步骤任务中，在确定方法前和宣布完成前各咨询一次。
  • 完成前先保存交付物。每次咨询之后，在继续工作前的下一条可见回复中重述关键指导。
  • 完整姿态下，已有证据与咨询建议指向不同方向时，再做一次协调咨询，不静默切换。

采纳规则与失败

默认采纳建议。按建议执行失败，或第一手证据反驳具体主张时，可以偏离并说明理由；自测通过不等于建议错误。建议与用户约束、授权或保留接口冲突时，直接拒绝并说明理由。

因推理缺陷拒绝不同模型顾问的建议前，先做一次协调咨询，说明证据与建议的冲突并问清取舍依据。同模型时可直接拒绝并解释。建议不授予授权、否决权或新要求。

返回值的 status=succeeded 表示结果与实际设置通过校验，kind 为 plan、correction 或 stop，并有非空 advice。成功的停止建议要求调用者停止并上报。status=failed 携带错误代码与原因，不包含建议。只开始但没有终态结果不算成功；失败后工作保持待定，直到咨询成功或用户放行，不自动重试。

验收设置与主会话责任

单一档位产出的工作使用同档顾问；多个档位共同产出时使用最高档。主会话自行产出的工作，选择不弱于主会话的最低顾问设置；没有合格项或模型未知时使用最强项。先比较模型，再比较推理强度。低置信度结论保持待定并交给用户，不自动换档复审。

主会话检查所有实际改动并拥有验收决定。它可以自己执行检查，也可以把完整检查范围交给核验者；有效证据可以复用。有实质修正时，核验修正并在全新线程复审。必需证据缺失或问题未解决时，不宣布完成。

第六章

钩子与运行核验

SessionStart 在主会话启动或恢复时注入所选姿态与采纳规则，不依赖技能是否加载。子代理从入口指令获取姿态，不重复注入。PostToolUse 在原生派发后自动核对实际模型和推理强度；模板固定值优先，否则使用调用方明确传入的值。

设置匹配时保持静默。缺少调用方强度、设置不匹配或缺失可靠证据时，派发会话收到工作待定消息。钩子最多等待两秒容许子会话证据落盘；之后缺失不能被当成成功。咨询组件还逐次验证每个顾问实际请求的模型、强度和空工具集合。

插件没有主会话 Stop 或执行者 SubagentStop 钩子，不自动拦截结束。咨询要求由调用者按姿态执行。两条钩子不写文件、不保留会话状态、不建立观察日志。

按需人工检查

sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_worker_crux_m --effort xhigh <native-thread-id>
sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_advisor_crux <native-thread-id>

检查器读取已发布模板核对角色、模型、强度、线程、父关联、目录和观察到的权限。调用方选择强度时必须传 --effort；固定强度时可省略，传入时必须相等。不带 --agent 的通用检查不能证明角色合同。

检查器不能证明授权、升级资格、任务完成、质量或强制隔离。只读角色请求只读权限，但宿主可能施加更宽权限；应区分请求、观察到的只读行为和宿主真正强制的隔离。

四组分别覆盖安装与入口一致性、检查器、咨询调用边界、钩子命令行边界。不带参数的检查包含四组，最终只需运行一次全组检查。镜像与手册测试分别检查对应关系和当前版本页面结构。真实派发与安装运行另作实测；静态检查不能证明真实模型行为或页面视觉一致。

第八章

本版边界

  • 只支持 Codex 的已验证接口与版本化插件缓存布局，不提供其他宿主适配、模型提供方桥或预算服务。
  • 咨询通过 Codex 原生认证调用模型，组件不读取、复制或传输凭据。为隔离工具，原生发现阶段可能启动已配置 MCP 服务，但不传入调用者上下文；咨询阶段禁用它们。
  • 有效上下文包括最新压缩替换历史、之后的消息与工具调用结果、当前未完成轮次。压缩已经移除的旧历史不会恢复，也不以摘要或固定轮数窗口替代。
  • 不支持的回滚、内容形状、不完整工具配对、身份不一致、上下文丢失或实际请求证据缺失都明确失败。只接受已验证的消息、图片和不透明推理等结构，不猜测未知结构。
  • 咨询的临时目录用于模型目录、请求证据和原生执行状态；完成或取消后清理。原生执行期限为 180 秒。调用失败不会自动重试，也不能算独立验收。
  • 主会话的正常启动应已初始化 Codex 配置目录。钩子信任由用户在宿主内管理，插件不授予信任，也不自行检测尚未信任的状态。
  • 路由实测证明入口能被发现并按设置执行，不证明质量、费用、稳定性或强制隔离。模型换代会使当前档位假设失效，需要重评。
  • 更窄的攻坚准入规则未启用；本版没有观察统计。Grok 路线留到 0.4.0。
第九章

相对上一版

上一版是 0.2.0。以下变化均由 ADR-0006 记录其决策依据。

工作分配

三个档位，十三个入口

主力、攻坚、后援按模型能力组织工作，推理强度只在档位内部细分，让日常工作与关键难点采用不同分配。

过程建议

咨询自动携带上下文

移除编写决策数据包的负担，保留未完成轮次与有效历史；无工具顾问提供第二次判断，独立验收仍另开线程。

  • 改light、standard、senior 改为主力、攻坚、后援。原来的首轮池与高级门槛退出，改为关键难点可直接进入攻坚、后援仅接收攻坚失败或用户声明。模型等级比推理强度更优先。
  • 改完整尝试与同设置返工合计才构成一次能力失败；随后升到下一档，原则上不在同档换模型、不降低模型等级。这样把普通排错与真正能力不足区分开。
  • 改路由表更新为 GPT-6 系列，入口从十一项增为十三项；六项固定强度，七项由调用方传入。安装器继续覆盖自有模板，并新增删除十一个 0.2.0 文件名。
  • 增无参数过程咨询取代决策包。自动重建有效上下文，使用原生认证和无工具顾问，并校验每次请求的模型、强度、工具与历史；不完整证据明确失败。
  • 增按调用者与顾问的精确模型标识选择完整或精简姿态。默认采纳，保留有依据的拒绝与协调咨询规则；咨询之后重述关键建议，不引入提交指令。
  • 增启动钩子注入主会话姿态，入口指令携带子代理姿态；派发钩子逐次核验设置，减少手动检查。首次安装和钩子改变后必须通过 /hooks 审阅。
  • 改独立验收不再使用固定默认档；它按工作最高档位或主会话设置选择顾问。低置信度交给用户，不自动提高顾问档位复审，避免咨询与验收混用。
  • 增咨询与钩子各有命令行边界测试，镜像覆盖新入口与规范姿态；完整检查覆盖安装、运行时、咨询、钩子四组。Grok 路线改为 0.4.0。
