第一章

安装与更新

需要带插件和原生自定义 agent 的 Codex 宿主，以及 jq。已装 marketplace 以 Git 为源，指向 GitHub 仓库 IpiggyI/codex-advisor，不是本地工作树。未推送的提交到不了已安装插件。

codex plugin marketplace add /absolute/path/to/codex-advisor
codex plugin add codex-advisor@codex-advisor
plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
test -n "$plugin_dir" && test "$plugin_dir" != null && test -d "$plugin_dir" && test -f "$plugin_dir/scripts/install-agents.sh" && sh "$plugin_dir/scripts/install-agents.sh"

配套安装器把十一个原生条目写到 $CODEX_HOME/agents；未设置时写到 ~/.codex/agents。本插件自己的已装文件若与模板不同则覆盖；退役的八个 0.1.0 文件名若还在则按文件名删除；其余文件一律不读不写，包括无关 agent、已有 Sol Advisor 文件、以及主会话配置。符号链接、非普通文件、非目录祖先、文件系统根、含点号路径段的目标，写入前拒绝。

安装后开一个新任务。确认宿主暴露 codex-advisor:orchestration，以及安装器列出的原生条目。插件安装和原生 agent 发现是两件分开的事，都要查。

sh "$plugin_dir/scripts/install-agents.sh" --check

--check 不写任何文件。漂移指清单里的文件缺失或与模板不同；残留指退役文件仍在。任一情况都失败，并列出每一项。

已推送到 origin 之后，每一侧按这次序更新

  1. codex plugin marketplace upgrade codex-advisor
  2. codex plugin remove codex-advisor@codex-advisor
  3. codex plugin add codex-advisor@codex-advisor
  4. 用下面这一行解析 plugin_dir：
    plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
  5. sh "$plugin_dir/scripts/install-agents.sh"
  6. 然后开一个新任务。

抽查用 sh "$plugin_dir/scripts/install-agents.sh" --check。

已装副本只由安装器写入，不要手改。开发用临时 CODEX_HOME；空的临时 --target-dir 只检查、不改正在用的配置。

第二章

使用方式

Use $codex-advisor:orchestration to implement and verify this feature.

主会话在使用者给出的目标、范围、保留决策、验收条件和资源限制之内，决定怎么拆、怎么排、哪些自己做、哪些派出去。常规分配不必每次问准许。不要为了省事去改这些边界。

Architect 模式

Architect 模式需要使用者明确授权。任意主模型都可以用。授权覆盖当前任务及其后续；无关任务要重新授权，除非使用者明确给了整段会话的范围。工单、规格、未接受的方案、或模型身份本身，都不会打开这个模式。把授权请求记下来。

打开之后，范围内的每一处实现编辑和修正都要派出去。主会话仍负责设计、合同、调度和验收，可以写设计和任务文件。

Use $codex-advisor:orchestration in Architect mode for this task.
第三章

十一个入口

入口按角色与档位命名，不按型号。一档若有两个型号，就有两个入口：_m 是默认候选，_h 是更强的备选。每个入口钉死型号；只有该格只允许一种推理强度时，才钉死 model_reasoning_effort。下面把 routing-profile.md 的表原样冻结在本版。

记法为 model[a*, b, c]：列出的每个推理强度都是首轮可选，* 是默认；一档两个型号时，列出顺序即候选顺序，› 分隔；钉死的强度写成 model[max]，表示条目固定 model_reasoning_effort，调用方不再传入。

第四章

首轮池、senior 门、升级梯

light 与 standard 合称首轮池。按结果对判断的依赖在两者之间自由选，没有先决条件；light 升到 standard 不是升级。默认取够用的最便宜拨盘及其默认强度。senior 只经过 senior 门：同一工作在首轮池内两次因能力导致的完整失败，或使用者宣布。Advisor 的门只看结论自称把握不足，或使用者宣布；worker 失败打不开它。

一次完整的 worker 尝试包含实现、普通排错和核对，然后验收失败，或明确做不完目标。中途测试失败和单次工具报错，不算完整失败。先分清环境问题、缺事实、合同缺口、推理失败、以及执行者是否合适。合同缺口是同一线程补合同，不是梯子上的一步。

验收失败之后走升级梯

  1. R1

    同一线程、同一拨盘发返工票，票里写清被违反的要求、可复现失败、预期行为和核对，不含修复。

  2. R2

    返工仍失败且原因是能力，开新线程接手，换同一型号的更高强度，或换另一型号。

  3. R3

    同一型号最多升一次。

  4. R4

    重大执行问题（工具反复失败、失控、碰到保留项）可以跳过返工票直接换型号，记为一次失败。

每次改推理强度或改型号都开新线程。同一型号同一强度的 worker 返工可以沿用原线程。换写者之前，停掉仍在冲突写入的前任，看实际改动，保留有用的部分。

第五章

Advisor 数据包

决策建议 · ca_advisor_standard

决策包

用于承诺前的判断。默认档是 standard，入口 ca_advisor_standard。必须问的情况：现行计划盖不住的关键决策；新证据推翻了计划里的关键前提；初步诊断之后失败原因仍不清楚；以及 senior 门是否成立。

独立验收 · ca_advisor_light

验收包

用于交付后的独立验收。默认档是 light，入口 ca_advisor_light。高风险交付，或使用者明确要求独立审查时，主会话检查之后必须再开一个全新线程发送验收包。先前的咨询或 worker 自评都不能代替。

两种数据包都由同一套 Advisor 入口回答，不再有单独的 reviewer 入口。senior 只在结论自称把握不足、或使用者宣布时使用。审查档位不跟主会话强度挂钩。有实质发现时先改、主会话再核、再开新线程审查改后的交付。

必需的执行跑不了、设置不受支持、证据缺失或互相打架、或实质发现未解决时，受影响的验收明确标为未完成。只读请求、观察到的只读行为、宿主强制隔离，三者分开报告。Explorer 和 Advisor 请求只读；宿主可能套用更宽的权限。

第六章

运行核验

形状是 --agent NAME [--effort E]。inspector 从该名称对应的已发布模板读取预期型号，以及钉死的强度。未钉死的入口必须传 --effort；已钉死的入口可省略，传入值必须等于钉死值。inspector 不判断某个强度是否属于允许集合，那是路由档案的事。

sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_worker_standard_m --effort xhigh <native-thread-id>
sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_advisor_light <native-thread-id>

角色核对要求观察到型号、强度、父线程关联、工作目录和权限。没有 --agent 时只发通用路由证据。inspector 不证明宿主支持、授权、新开调用、任务完成或强制隔离。0.1.0 的按角色选项已退役，改用 --agent。

第七章

中文孪生与检查清单

每个 plugins/codex-advisor/**/*.md 和每个 plugins/codex-advisor/agents/*.toml 在 docs/zh/ 下有一份中文孪生。Markdown 一对一存在。TOML 孪生可解析，且 name、model、model_reasoning_effort、sandbox_mode 与模板相等，两段散文为中文。镜像只在仓库里，不随插件下发。当前编排政策以 ADR-0004 为准。

sh plugins/codex-advisor/scripts/verify.sh --installation
sh plugins/codex-advisor/scripts/verify.sh --runtime
sh plugins/codex-advisor/scripts/verify.sh
python3 tests/test_zh_mirror.py
python3 tests/test_version_manual.py
git diff --check

verify.sh 分安装与运行时两组。test_zh_mirror.py 核孪生存在与 TOML 键相等。test_version_manual.py 核当前 plugin.json 版本对应的说明书页面。这些检查证明安装、分配和证据一致性。小规模原生冒烟不证明普遍质量、稳定或省钱。

第八章

本版边界

  • 只支持 Codex，没有其他宿主适配。
  • 没有调度器、提供方桥、预算服务；拨盘在插件内的路由档案，不是用户级配置档案。
  • 安装器覆盖本插件自有文件并删除退役名，但不改主会话配置，也不动清单和退役清单以外的文件。
  • 只读隔离不由插件强制。只读请求、观察到的只读行为、宿主强制隔离，三者分开记录。
  • 实跑只证派发不证质量。路线核对证明入口可发现、按模板型号启动、并按钉死或传入的强度运行；不证明隔离、质量、成本或稳定。
  • gpt-5.6-terra 与 Luna max 在本账号可调用；Luna xhigh 未实跑。依据是验收记录 .scratch/tier-role-pool/acceptance.md 于 2026-09-17 的表，宿主 codex-cli 0.154.0。

  • 改首轮池与 senior 门取代「按判断可直派 senior」。主会话按自己的难度判断，会把常规工作派到最贵档。对应工单 02。
  • 改升级梯 R1–R4 取代「无固定梯」。同一型号不应连升三次强度。对应工单 02。
  • 改reviewer 并入 Advisor 的两种请求形状（决策包与验收包）。第四个角色名只对应 Advisor 的一种请求。对应工单 01。

  • 删术语 Implementer 退役，改称 Worker。一个概念只用一个名字。对应工单 01、07。
