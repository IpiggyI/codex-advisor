第一章

安装与更新

需要支持插件、原生自定义代理、MCP 和钩子的 Codex，以及 Python 3.11 或更新版本、POSIX 命令行和 jq。Windows 上的钩子和 MCP 服务器通过 sh 启动，所以 PATH 必须包含 Git for Windows 的 bin 目录，例如 C:\Program Files\Git\bin；PATH 中只有 Git 的 cmd 目录时，Codex 启动时提示 codex_advisor 的 MCP 启动失败：program not found。Windows 过程咨询还需要 PATH 中的原生 codex.exe。本版在 Codex 0.160.0 上核验；宿主协议、会话记录或缓存布局变化后，需要重新核验。若提供方使用 S2A_API_KEY，启动 Codex 的进程必须已设置该变量；插件通过 MCP 的 env_vars 转发它。其他变量名需要修改源码清单并更新插件，不会自动继承。

codex plugin marketplace add https://github.com/IpiggyI/codex-advisor.git
codex plugin add codex-advisor@codex-advisor
plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
test -n "$plugin_dir" && test "$plugin_dir" != null && test -d "$plugin_dir" && test -f "$plugin_dir/scripts/install-agents.sh" && sh "$plugin_dir/scripts/install-agents.sh"
sh "$plugin_dir/scripts/install-agents.sh" --check

配套安装器将十七个入口写入 $CODEX_HOME/agents，未设置时使用 ~/.codex/agents。它只写入本插件缺失或内容不同的模板，不删除任何文件，也不读写目标目录中的其他文件或主会话配置。符号链接、非普通文件、不合法祖先和危险目标路径会在写入前被拒绝。

安装后打开全新交互会话，在 /hooks 中审阅并信任 SessionStart、PreToolUse 和 PostToolUse 三条插件钩子。安装或启用插件不会授予信任。尚未信任时，宿主跳过钩子并显示启动警告。分别确认编排技能、十七个入口和 codex_advisor MCP 服务器的 process_consultation 工具已发现。

更新每一侧安装

已安装市场从 GitHub 仓库获取版本；未推送的提交不会进入安装副本。WSL 和 Windows 使用各自的原生 Codex 与配置目录。Windows 中的这些命令需要 Git Bash 及相应依赖。

codex plugin marketplace upgrade codex-advisor
codex plugin add codex-advisor@codex-advisor
plugin_dir="$(codex plugin list --json | jq -r '.installed[] | select(.pluginId == "codex-advisor@codex-advisor") | .source.path')"
sh "$plugin_dir/scripts/install-agents.sh"
sh "$plugin_dir/scripts/install-agents.sh" --check

--check 只检查，不写文件；有模板缺失或内容不同时，它失败并逐项列出。最后在每一侧开启全新任务；钩子定义是新增的或有变化时，在 /hooks 中审阅并信任。信任绑定当前钩子的哈希值，所以旧的信任不覆盖变化后的钩子。

不要手改已安装入口。开发时只在临时 CODEX_HOME 中添加本地仓库路径；不要把真实安装改指向未发布工作树。

第二章

使用方式

使用 $codex-advisor:orchestration 实现并验证这项功能。

任意主会话都可以自己实现、委派，或两者并用。主会话负责目标、拆解、调度和验收，在用户的范围、保留决策与资源限制内选择执行方式。普通分配不需要逐次请求许可。

探索者只读收集证据、来源位置和缺口。执行者接收目标、文件归属、接口、约束和核验要求，负责局部实现与排错，保留其他人的改动，不再委派实现。顾问负责过程建议或独立验收；两者入口和上下文要求不同。

任务有两张以上工单时，第一次派发前把整个任务的依赖、契约、归属、工作目录隔离和核验批次写入任务件。共用文件或同一区域的工作合并为一份契约；并发契约使用独立目录，或者串行执行。每份契约只等待自己的真实依赖。共用昂贵准备的检查按完整范围合并，写明由谁执行、何时执行；提交边界按授权和回滚需要确定，与验收批次分开。

技能按事件加载与阅读

以下事件需要使用编排技能：主会话被要求委派或即将委派，即将验收、返工或升级委派结果，用户授权 Architect 模式，交付需要独立验收，或主会话、执行者、探索者缺少适用的姿态块或采纳块。不属于这些事件的直接工作不加载技能。过程咨询本身不是加载事件。

SKILL.md 只写每个事件都要用的公共路径：授权与 Architect 模式、角色与档位选择、委派合同要点、调度、普通验收和咨询规则。它还写有事件与参考文件的对照，并在每个指针后保留一条关键规则；主会话还没有读取参考文件时，这条规则已经生效。

只做设计与调度的模式

本任务使用 $codex-advisor:orchestration 的 Architect 模式。

Architect 模式需要明确授权，覆盖当前任务及其后续。主会话保留设计、合同、调度和验收；范围内每一处实现编辑和修正都必须委派。工单、规格、模型身份或未接受方案本身不会打开该模式。无关任务需要新授权，除非用户明确授权整段会话。

第四章

准入与升级

通常从主力开始。已识别关键难点，或多个约束需要联合处理时，可以首轮进入攻坚。攻坚没有使用配额。后援只能在攻坚发生能力失败后，或由用户明确声明启用。

完整尝试包含实现、排错和核验，最终验收失败或确实无法完成。原尝试与同一设置的返工都失败，且原因归于能力，合计才算一次能力失败。环境问题、缺失事实、合同缺口和中途测试失败不推动升级。选择满足难点或升级下限、用户声明和准入依据的最低档位；只声明型号不授权后援档位。

  1. R1

    先发同一设置的返工票，说明被违反的要求、复现、预期行为和核验方法。符合续用窗口时使用原线程；否则携带交接材料开新线程。

  2. R2

    返工后形成能力失败，按主力、攻坚、后援、用户的顺序移交。除非没有其他选择，不在失败档位内换模型，也不降低模型定位。同模型接手必须提高强度。

  3. R3

    同一模型最多提高一次强度。模型、强度或角色改变都需要匹配入口的新线程；同设置返工还须满足续用窗口。换线程保留档位、设置和能力失败历史。

  4. R4

    工具反复失效、失控或触碰保留项等重大执行问题，可以跳过返工，记为一次能力失败。

从攻坚起步的任务在一次攻坚能力失败后进入后援。移交前停止冲突写者，检查实际状态，保留有用改动，并交接已完成项、失败证据和剩余工作。完整的恢复规则和交接模板在 references/recovery.md。

执行者的三十分钟续用窗口

返工、修正契约、恢复工作和新票都要求同一角色、型号和强度，并且宿主记录的最近活动距现在不超过三十分钟。恰好三十分钟允许续用。时间缺失、无效、没有时区、在未来或超窗时，新开同设置线程，带上原契约、缺陷、上轮报告和核验结果。新票还必须在同一区域，并确实需要已有上下文。探索者调用和独立验收始终开新线程。这个窗口是续用政策，不代表实测缓存寿命。

每次派发与续发都声明路由

新派发的 message 第一行与 task_name 完全相同；空一行后写路由，再空一行写角色数据包。新线程使用 fork_turns: none。下面是攻坚执行者的消息格式：

wire_http_checks

Route: role=worker tier=crux dial=gpt-6.1-sol[xhigh] basis=key-difficulty ref=issues/02-route-gate.md

在此填写目标、归属、接口、约束和核验要求。

followup_task 与 send_message 的消息直接从路由行开始，空一行后写数据包或修正内容。目标可以是线程 UUID、绝对任务路径或相对任务路径；未知或歧义目标被拒绝。向已解析的主会话或非插件入口发送消息不需要路由。主力档位省略 basis 与 ref，例如 Route: role=worker tier=mainstay dial=gpt-6-luna[max]。

角色攻坚依据后援依据
执行者与探索者key-difficulty、failure、user-declarationfailure、user-declaration
顾问acceptance-mapping、user-declarationacceptance-mapping、user-declaration

ref 必须指向相应的难点约束、失败与诊断、用户声明，或验收范围与映射。钩子检查格式、入口与设置是否兼容、宿主身份和时间条件；调用方仍负责依据真假、用户授权、最低适用档位和共享上下文的必要性。

第五章

过程咨询与独立验收

过程咨询

自动携带上下文

主会话、执行者和探索者以空对象调用 process_consultation。顾问自动取得当前有效上下文，没有工具，返回计划、修正或停止建议。调用者不用编写摘要或数据包。

独立验收

新线程检查交付物

高风险工作或用户明确要求独立审查时，主会话检查后，另开顾问线程发送验收数据包。顾问检查真实改动与证据；过程咨询、执行者自评和检查执行不能代替它。

探索者和执行者在本档的顾问格中，选择不弱于自身设置的最低一项；没有这样的设置时，选择该格最强的一项。按本版路由表，gpt-6-luna 和 gpt-6.1-sol 入口咨询 gpt-6.1-sol，gpt-6-astra 入口咨询 gpt-6-astra。主会话在所有档位的顾问设置中，选择不弱于自身设置的最低一项；没有合格设置时，选择最强设置 gpt-6-astra[xhigh]；模型标识不在路由表中时，使用 gpt-6.1-sol[xhigh]。例如 gpt-6.1-sol 主会话在 low 和 medium 下咨询 gpt-6.1-sol[medium]，在 high、xhigh 和 max 下咨询同强度的 gpt-6.1-sol。咨询顾问没有自己的升级路径。

按精确模型标识选择咨询姿态

  • 调用者与顾问模型不同，使用完整姿态：实质工作前、遇到阻滞时、改变方法前、宣布完成前咨询。定向找文件和读来源不算实质工作。短任务的下一步直接由刚读到的工具输出决定时，可以免于咨询。
  • 模型相同，使用精简姿态：只在多步骤任务中，在确定方法前和宣布完成前各咨询一次。
  • 完成前先保存交付物。每次咨询之后，在继续工作前的下一条可见回复中重述关键指导。
  • 完整姿态下，已有证据与咨询建议指向不同方向时，再做一次协调咨询，而不是不作说明就切换方向。

采纳规则与失败

默认采纳建议。按建议执行失败，或第一手证据反驳具体主张时，可以偏离并说明理由；自测通过不等于建议错误。建议与用户约束、授权或保留接口冲突时，直接拒绝并说明理由。

因推理缺陷拒绝不同模型顾问的建议前，先做一次协调咨询，说明证据与建议的冲突并问清取舍依据。同模型时可直接拒绝并解释。建议不授予授权、否决权或新要求。

返回值的 status=succeeded 表示结果与实际设置通过校验，kind 为 plan、correction 或 stop，并有非空 advice。成功的停止建议要求调用者停止并上报。status=failed 携带错误代码与原因，不包含建议。只开始但没有终态结果不算成功；未禁用时，失败后工作保持待定，直到咨询成功或用户放行，不自动重试；禁用后的处理见下段。

咨询失败时，调用者在下一条可见回复中说明失败，不把失败当作建议，也不宣布咨询已完成。每个线程累计第四次失败后，consultationDisabled=true 禁用后续咨询；成功调用不清零，恢复线程或重启组件也不清零。禁用后停止咨询调用，报告咨询不可用，继续已授权工作；用户审批与独立验收仍然适用。

验收设置与主会话责任

委派工作使用参与档位中最高档的顾问格，在格内选择不弱于参与工作最强设置的最低一项。主会话自行产出的工作，选择不弱于主会话的最低顾问设置；两个入口都允许该设置时，使用较低档位的入口。没有合格设置时使用 ca_advisor_rescue_h；模型标识不在路由表中时，使用 ca_advisor_crux_m，强度为 xhigh。先比较模型定位，再比较推理强度；定位从入门、中端、高端到旗舰，强度从 low、medium、high、xhigh 到 max。低置信度结论保持待定并交给用户，不自动换档复审。

主会话检查所有实际改动并拥有验收决定。它可以自己执行检查，也可以把完整检查范围交给核验者；有效证据可以复用。有实质修正时，核验修正并在全新线程复审。必需证据缺失或问题未解决时，不宣布完成。

第六章

钩子与运行核验

SessionStart 在主会话启动或恢复时注入所选姿态与采纳规则，不依赖技能是否加载。启动事件不带推理强度，所以钩子按每一种强度计算主会话对应的顾问模型；结果随强度变化时，只注入工作待定消息。按本版路由表，gpt-6.1-sol 和 gpt-6-astra 主会话得到精简姿态，其他模型得到完整姿态。子代理从入口指令获取姿态，不重复注入。PostToolUse 在每次 ca_* 原生派发后，核对子线程的角色、父线程、会话和任务路径与宿主记录一致，并核对宿主记录的模型和推理强度；模板固定值优先，否则使用调用方明确传入的值。

PreToolUse 在 spawn_agent、followup_task 和 send_message 执行前检查路由。不合规时返回拒绝决定；合规时给出路由确认。没有这条确认，自动准入检查保持未验证，调用方需手动核对声明与资格。

实际设置匹配时，PostToolUse 另外发出下面这一行确认，其中 {role} 是入口名：

Codex Advisor: {role} identity, model, and effort match the host record at {model}[{effort}]; working directory and permissions were not checked.

缺少调用方强度、设置不匹配或证据缺失、冲突时，派发会话收到工作待定消息。派发到非 ca_* 入口时没有任何消息。ca_* 派发之后没有任何消息，说明钩子没有运行，例如钩子尚未被信任；这次派发未经检查，不能当作已核实。钩子最多等待两秒容许子会话证据落盘；之后缺失不能被当成成功。咨询组件还逐次验证每个顾问实际请求的模型、强度和空工具集合。

路由确认和实际设置确认分别证明派发前声明合规、派发后设置匹配。检查器通过不能证明派发前钩子执行过。三条钩子不写文件、不保留持久状态，也不读取配置或凭据。没有钩子会自动阻止结束；咨询要求由调用者按姿态执行。

何时运行检查器

每次派发都要核对角色、模型、强度、线程、父关联、工作目录和观察到的权限。原生派发与详情的公开元数据是权威来源；检查器补足元数据缺少的字段，不推翻矛盾。钩子从不检查工作目录和权限。以下两种情况由调用方自己运行检查器：ca_* 派发没有任何钩子消息；原生元数据缺少工作目录或权限。

sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_worker_crux_h --effort low <native-thread-id>
sh "$plugin_dir/scripts/inspect-agent-runtime.sh" --agent ca_advisor_crux_h <native-thread-id>

检查器读取已发布模板核对角色、模型、强度、线程、父关联、目录和观察到的权限。调用方选择强度时必须传 --effort；固定强度时可省略，传入时必须相等。不带 --agent 的通用检查不能证明角色合同。

检查器不能证明授权、升级资格、任务完成、质量或强制隔离。只读角色请求只读权限，但宿主可能施加更宽权限；应区分请求、观察到的只读行为和宿主真正强制的隔离。

第七章

中文镜像与检查

每个运行时 Markdown 和入口 TOML 在 docs/zh/ 下有同路径中文镜像。入口的名称、模型、推理强度和沙箱设置保持一致。镜像只在仓库保存，不随插件发布；版本手册没有 Markdown 副本。本版主要决策见 ADR-0006、ADR-0007、ADR-0008、ADR-0009、ADR-0010 和 ADR-0011。

插件只携带运行时脚本。维护者检查脚本及其夹具在仓库的 tests/ 下，不随插件发布；以下命令都从仓库根目录运行。

sh tests/verify.sh --installation
sh tests/verify.sh --runtime
sh tests/verify.sh --consultation
sh tests/verify.sh --hooks
sh tests/verify.sh
python3 tests/test_zh_mirror.py
python3 tests/test_version_manual.py
python3 tests/test_shipped_wording.py
git diff --check

四组分别覆盖安装与入口一致性、检查器、咨询调用边界、钩子命令行边界。不带参数的检查包含四组，最终只需运行一次全组检查。镜像与手册测试分别检查对应关系和当前版本页面结构；成品措辞检查覆盖已知维护叙述、规范模型名、拨档和两份定位表的一致性。真实派发与安装运行另作实测；静态检查不能证明真实模型行为或页面视觉一致。

第八章

本版边界

  • 只支持 Codex 的已验证接口与版本化插件缓存布局，不提供其他宿主适配、模型提供方桥或预算服务。
  • 咨询通过 Codex 原生认证调用模型，组件不读取、复制或传输凭据。为隔离工具，原生发现阶段可能启动已配置 MCP 服务，但不传入调用者上下文；咨询阶段禁用它们。
  • 有效上下文包括最新压缩替换历史、之后的消息与工具调用结果、当前未完成轮次。压缩已经移除的旧历史不会恢复，也不以摘要或固定轮数窗口替代。
  • 不支持的回滚、内容形状、不完整工具配对、身份不一致、上下文丢失或实际请求证据缺失都明确失败。只接受已验证的消息、图片和不透明推理等结构，不猜测未知结构。
  • 咨询的临时目录用于模型目录、请求证据和原生执行状态；完成或取消后清理。原生执行期限为 180 秒。调用失败不会自动重试，也不能算独立验收。
  • 主会话的正常启动应已初始化 Codex 配置目录。钩子信任由用户在宿主内管理，插件不授予信任，也不读取信任状态。未信任、超时或执行失败的钩子不能保证阻断。缺少路由确认或实际设置确认时，对应检查保持未验证；收到工作待定消息，表示检查已经运行但没有通过。
  • Windows 上的钩子由 PowerShell 执行 commandWindows。设置了 CODEX_HOME 时，宿主以 \\?\ 形式传入插件路径，sh 无法打开这个路径，钩子失败。宿主改用 cmd.exe 执行钩子时，$env:PLUGIN_ROOT 不会展开，钩子同样失败。
  • 安装器不删除任何文件。--check 只报告本插件模板的缺失与不同，不报告目标目录中的其他文件。从 0.3.0 更新后，旧文件 ca-advisor-mainstay.toml、ca-advisor-crux.toml、ca-advisor-rescue.toml 和 ca-worker-rescue.toml 可能仍留在目标目录，--check 不报告它们。派发前钩子正常执行时，已从路由表移除的插件入口被拒绝；旧的 ca_worker_rescue 发起过程咨询也会被拒绝。
  • 路由实测证明入口能被发现并按设置执行，不证明质量、费用、稳定性或强制隔离。模型定位是用户声明的路由值，不是质量或速度的测量结果。模型换代时，需要重新评估该模型的定位、咨询与验收映射，以及涉及它的升级路径。
  • 路由表中没有的主会话模型咨询 gpt-6.1-sol[xhigh]，自行产出的工作也由这一设置验收。这个模型强于 gpt-6.1-sol 时，顾问弱于主会话；新模型应先加入路由表再作为主会话使用。
  • 本版不提供 Grok 路线，该路线留到 0.4.0。

路由与续用

执行前校验声明和窗口

派发与续发都声明角色、档位和设置。执行者只有在三十分钟窗口内、身份与设置匹配时才能续用。

  • 增多票任务首次派发前写入整体规划，共用区域合并契约，并发契约隔离目录，核验按批次执行。
